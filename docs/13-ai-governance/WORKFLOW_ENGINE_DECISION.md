# 工作流引擎技术决策

## 当前决策
MVP 使用 PostgreSQL 持久化业务工作流状态 + Outbox + Celery 执行队列。Workflow/Node 状态由业务应用层控制，Celery 不作为唯一状态来源。

## 原因
当前主要需求是单体内部异步任务、模型调用、媒体渲染、审核等待和可恢复执行。该组合与现有技术栈一致，运维复杂度较低。

## 必须具备
幂等键、Attempt 历史、Outbox、租约/心跳、有限重试、指数退避、取消传播、Checkpoint、Webhook 幂等、孤儿任务恢复、队列隔离和监控。

## Temporal 评估触发条件
出现长时间人工等待/复杂补偿、跨系统工作流、自研恢复机制维护成本持续升高，且团队能承担 Temporal 运维时，启动 Spike。比较开发复杂度、恢复语义、可观测性、部署备份、迁移成本和故障模式。

## 迁移原则
如采用 Temporal，由 ADR 定义流程迁移范围、业务状态映射、历史运行完成策略、回滚路径和数据一致性。Temporal 接管编排后不再双写两套流程引擎。Celery 可保留为短任务执行器，但职责必须明确。
