## 2. 文档类型与模板

### 需求文档
- 背景/目标/非目标
- 用户角色与前置条件
- 主流程/异常流程
- 功能规则与权限
- 验收标准（可测试、可观察）
- 依赖、风险和未决问题

### 技术设计文档
- 状态：Draft / In Review / Accepted / Deprecated
- 背景与问题
- 约束和备选方案
- 决策及理由
- 模块边界、数据模型、接口和流程
- 安全、可靠性、性能
- 测试与迁移方案
- 风险、回滚、关联 Issue

### ADR 架构决策记录
文件名：`docs/01-architecture/adr/ADR-NNNN-title.md`。
包含状态、日期、上下文、决策、备选方案、后果和相关决策。已接受 ADR 不直接覆盖，后续通过新 ADR 取代。

### 运维/测试文档
写明适用版本、环境前置条件、操作步骤、验证方式、失败处理和回滚步骤。

## 3. 更新机制

- 需求变化：更新需求文档和关联 Issue。
- 架构/数据/API 变化：同一 PR 更新设计文档、OpenAPI/数据字典/ADR。
- 新增配置：更新 .env.example 和部署文档。
- 缺陷修复：必要时补充故障原因、回归测试和运维提示。
- 每次发布：更新版本说明、迁移说明和已知问题。

## 4. 版本与状态

文档与代码同仓库、同 PR、同 Git 历史；文档变更通过 PR 审核。标注状态和最后更新日期；不复制多个互相冲突的“最新版”。废弃文档保留历史并标记 Deprecated，链接到替代文档。

## 5. 写作要求

中文为主，技术名词保留英文；术语一致；图使用 Mermaid；命令可复制；避免未验证的“已实现”表述。每项设计决策区分已确认、建议和待确认。
