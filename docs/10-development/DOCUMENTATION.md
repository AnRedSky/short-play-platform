# 文档规范

## 结构
采用 docs/README.md 唯一入口，按编号领域组织。总体方案负责统一边界和索引；领域文档负责具体规范，不复制完整内容形成平行版本。

## 统一章节
适用范围/目标；术语；需求/规则；设计/流程；数据与接口；权限/安全；异常与恢复；测试/验收；依赖/风险（如适用）。

## 规范用词
必须/MUST 表示强制要求；建议/SHOULD 表示默认方案，例外需说明；可选/MAY 表示按需启用。区分已确认决策、建议和待决事项，不使用模糊的“应该已完成”。

## 文档类型
需求文档含背景、目标、用户流程、规则、权限、验收；技术设计含约束、备选、决策、模块、数据、接口、可靠性、安全、测试和迁移；ADR 含状态、日期、背景、决策、备选、后果和关联；运维文档含环境、步骤、验证、失败处理和回滚。

## 更新
需求变化同步需求文档与 Issue；架构/数据/API 变化同步 ADR、迁移和契约；配置变化同步 .env.example 与部署文档；每次发布同步版本、迁移、已知问题。文档与代码在同一 PR 更新。

## 版本
当前有效内容只保留一个正式入口。历史通过 Git 提交追溯；被替代内容不得继续作为当前操作规范或重复维护的“最新版”。被接受 ADR 不覆盖，后续新 ADR 明确取代关系。

## 2026-11-18 文档唯一基线补充

当前实施基线唯一入口为 `docs/01-architecture/IMPLEMENTATION_BASELINE.md`；页面级功能与交互唯一入口为 `docs/02-requirements/FEATURE_INTERACTION_SPEC.md`；阶段交付顺序以 `docs/10-development/ROADMAP.md` 为准。具体领域文档负责细节，不得重新定义与基线冲突的项目边界。

所有功能文档必须区分“当前代码状态”和“目标要求”；接口目录/页面入口/ORM 模型存在不等于功能完成。状态更新需附对应 commit、迁移、测试和 CI 证据。
