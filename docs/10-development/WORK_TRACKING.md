# 开发任务跟踪与协作机制

## 1. 工具约定

以 GitHub Issues 作为任务唯一事实来源，Pull Requests 关联 Issue；GitHub Projects（若团队启用）作为看板视图。代码、规范和文档以仓库为准；即时通讯只用于提醒，不作为任务状态记录。

## 2. Issue 分类

- Epic：阶段/领域目标，汇总多个交付任务。
- Feature：可独立验收的功能。
- Bug：实际行为与预期不一致。
- Task：工程、测试、文档或运维任务。
- Spike：有时间盒的技术验证，必须输出结论。

## 3. 标签建议

type: feature/bug/task/docs/spike；priority: P0/P1/P2/P3；area: backend/frontend/ai/workflow/media/security/devops/docs；status: blocked/needs-review。标签用于检索，不替代 Issue 正文状态。

## 4. Issue 模板

```markdown
## 背景与目标
## 范围 / 非范围
## 前置依赖
## 实施拆分
- [ ] ...
## 验收标准
- [ ] 可观察、可复现、可自动化验证的结果
## 测试要求
## 文档/迁移/配置影响
## 风险与回滚
## 负责人 / 目标日期
```

## 5. 状态流转

Backlog → Ready → In Progress → In Review → Done；遇阻转 Blocked，并在 Issue 中说明阻塞原因、影响、责任人、下一步和预计解除时间。GitHub Projects 的状态字段可映射上述流程；若未启用 Projects，以 Issue 状态、标签和里程碑维护。

## 6. 任务拆分规则

- 一个 Issue 尽量对应 0.5–3 个工作日的可验收工作。
- 大于 3 天的任务拆成子任务；跨领域工作拆分并标明依赖。
- 每个任务必须有唯一负责人、优先级、目标日期和验收标准。
- P0 为主链路阻断/安全/数据正确性；P1 为 MVP 必需；P2 为增强；P3 为后续优化。
- 依赖关系写入 Issue 正文；阻塞任务不得进入 Ready。

## 7. 日常协作节奏

- 开始任务：负责人将 Issue 移至 In Progress，建立 feature/fix/docs 分支。
- 每日同步：更新进展、剩余工作、风险和阻塞；不要求长篇日报。
- 提交 PR：关联 Issue，填写测试证据、影响和回滚说明。
- 审查：审查者检查业务正确性、安全、测试、可维护性和文档。
- 合并：CI 通过、审查完成、验收标准满足后合并。
- 关闭：合并后由负责人核对线上/环境验收和文档，再关闭 Issue。
- 阻塞：当天上报；涉及数据安全、凭据泄露、数据损坏立即升级处理。

## 8. 进度口径

状态含义必须一致：未开始、进行中、评审中、阻塞、已完成。百分比只作辅助，不能替代交付物和验收项。阶段完成以全部 P0/P1 任务通过验收为准。
