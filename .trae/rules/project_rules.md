# 项目规则

## 一、项目性质与开发原则

1. 本项目是真实业务项目，不是演示项目、练习项目或原型玩具。所有需求判断、流程设计、数据结构、页面交互和验收标准，均以真实业务落地为最终目标。
2. 当前项目处于开发初期，尚未接入真实后端服务。现阶段的模拟后端只用于满足前端开发、调试和联调需要，确保前端功能可以独立推进，不代表最终业务实现。
3. 模拟后端、临时状态、演示数据和占位逻辑均属于可替换的过渡层。不得因为模拟实现方便而降低业务规则、权限约束、状态流转或数据一致性的要求。
4. 现有代码架构、实现逻辑或数据结构如果无法支撑真实业务场景的长期迭代，可以经过评估后彻底重构，包括推翻旧实现、重建领域模型、清理历史遗留数据、迁移旧数据。重构不受现有临时方案约束。
5. 重构必须以真实业务落地和长期可维护为核心准则，先说明影响范围、迁移路径、回退方式和验收标准，再执行改造，避免无边界推翻。
6. 页面契约、领域模型和业务流程应尽量与具体后端实现解耦。真实后端接入时，模拟层可以替换，业务语义和用户可见流程不得整体推倒重来。
7. 验收以真实业务流程是否闭环、状态是否正确、权限是否有效、数据是否一致为准。演示数据只能用于验证功能，不能作为业务结论或交付依据。

## 二、语言规范

1. 所有面向用户的说明、方案、总结、验收记录、需求描述、文档正文和界面文案，统一使用规范中文完整表达。
2. 中文语句中不得夹杂英文单词、英文缩写、专业英文简写，也不得出现与中文混排的非中文字母符号。
3. 阶段、版本、基线、任务、产物等业务概念一律使用中文全称，例如“第二执行阶段”“镜头计划版本”“视觉基线”“候选镜头版本”，不得用字母代号代替。
4. 同一概念首次出现使用中文全称，后续可使用明确、统一的中文简称。
5. 句子应完整、通顺、主谓明确，避免只写关键词、英文式倒装和生硬直译。
6. 标点统一使用中文标点，数字与中文之间按中文排版习惯处理。

## 三、技术标识的处理

1. 代码、命令、文件路径、接口字段、数据库字段、程序标识等必须保留原始写法的内容，只能放在独立代码块中。
2. 上述原始标识不得直接嵌入中文句子，不得用括号夹在中文词语后面冒充业务名称。
3. 正文解释技术标识时，先给出中文含义，再在独立代码块中列出原始写法。
4. 页面提示、按钮、错误信息、验收说明和提交说明属于用户可见文本，应优先使用中文；技术原始信息可另起代码块保留。

## 四、适用范围

1. 适用于需求分析、方案设计、流程梳理、开发说明、验收报告、问题排查、代码注释、提交说明、文档标题与正文。
2. 代码本身、第三方原始日志、外部系统强制要求的字段不受此规则约束，但引用时必须用中文说明其作用。
3. 本规则与旧有英文命名习惯冲突时，以本规则为准；代码内部标识和既有接口字段暂不强制重命名。
4. 前端设计、交互、重建方案、接口契约和测试文档统一存放在前端文档目录，目录位置如下：

```text
web/docs
```

5. 前端文档按“重建方案、垂直切片、模块契约、归档资料”分类存放，不把多个流程混在一份文档里。

## 五、检查要求

1. 交付前检查正文是否出现非中文词语或字母缩写。
2. 发现英文缩写时，改写为中文全称或中文简称。
3. 发现中英文混排的技术标识时，移入独立代码块并补充中文解释。

## 六、重构与重建规则

1. 重构或重建前必须先完成真实业务基线梳理，明确业务对象、状态流转、权限边界、数据归属、异常处理和验收用例。业务基线未确认前，不得大规模改动代码结构。
2. 如果现有架构、实现逻辑或数据结构已经无法支撑真实业务，允许受控重建：领域模型、状态机、接口契约、页面结构和测试基线从零定义，旧代码只作对照，不作为新实现的依赖。
3. 受控重建不等于一次性删光旧代码。旧实现和旧文档在新链路通过验收前只作参考；新链路验收后，再按迁移清单清理，避免在替代方案尚未可用时丢失已验证的业务规则。
4. 每个功能进入开发前必须具备清晰的功能契约，至少包含目的、使用角色、入口、前置状态、输入数据、操作结果、后置状态、失败处理、权限要求、审计要求和验收用例。缺少上述内容的功能视为未定义，不得开始实现。
5. 每次只推进一个可独立验收的流程。禁止把多个未验证流程打包成一次大重构，禁止在没有验收标准的情况下边写边改。
6. 旧文档与旧实现如果与新业务基线冲突，应先标记为历史资料并说明替代关系，再从主文档和主源码中清理。清理前必须保留迁移清单和受影响功能清单。
7. 旧数据清理或迁移必须可回退。执行前说明数据范围、迁移规则、校验方式、回退方式和责任边界，不得以“重构需要”为由直接删除业务数据。
8. 前端重建后，页面、组件、状态管理、数据访问和模拟数据适配层必须分层清晰。页面组件不得直接承载业务规则，模拟数据层不得成为业务事实来源。
