# 交互复核与页面功能方向（v9.7.0 · 2026-11-25）

承接 `REVIEW-SIMPLIFY-V9.7.0.md`（布局/列宽）。本轮补第三个维度：**页面怎么用**——能不能查到、能不能改、改完往哪走。
证据脚本：`tools/_audit_ux.mjs`（快照 `tools/_ia_ux.txt`），逐页渲染后按动作处理体反查承载方式（抽屉 / 弹窗 / 跳转 / 状态切换 / 写入），并统计表长、查询控件、行内动作密度。

## 一、结论

**可以继续简洁，但"删内容"这条路已经走完**。56 页里内容冗余已清零（`_audit_overlap` 真双入口 0），现在的瓶颈是三个"用起来费力"的点：48 页有表格只有 1 页能搜索、行内动作堆到 5 个、同一语义（查看）承载方式不统一。功能层面不需要再合并路由——56 条已是这套信息架构的下限（D1/D2 已定），下一步是**页内分层**而不是继续拆并页面。

## 三、页面功能方向

1. **不再合并路由**：B2 已把 65 压到 56，再合并会把「下钻层级」（`orgs/member`、`projects/detail`、`projects/new`）也吃掉，破坏 D1 的边界。
2. **页内分层是唯一还在动的方向**：一页固定四段——查询区 → 主表/主卡 → 详情抽屉 → 页尾一条说明。超出部分用 tab，不加第 6 张卡。
3. **三类页面各有不同的"减法"**：
   - 台账操作型（38 页）：减列宽、加查询、行内留主操作，其余进抽屉；
   - 只读台账型（10 页）：不加操作，改为「一张主表 + 一条结论」，把决策留给对应执行页；
   - 任务型（6 页）：保持单卡单流程，禁止在任务页塞台账（`projects/new`、`creation/brief` 已符合）。
4. **剩余可量化空间**（与上一份文档同源）：卡 ≥6 的 10 页、列 ≥9 的 17 页、提示 ≥2 的 20 页、单卡 ≥40% 的 18 页。

## 四、交互方向：五条规范

- **I-1 查询优先**：凡主表 ≥8 行，页面顶部必须有 `.toolbar`，内含 `input.search[data-filter]` + `[data-filter-count]`；状态类再加 `seg-chip`。计数按整页聚合（已改 `applyFilters`），多表页面不再只统计最后一张。
- **I-2 行内 ≤2 个动作**：主操作（测试 / 处理 / 查看）+ 一个「管理」入口；写操作与不可逆动作一律进抽屉或弹窗，不在表格行里平铺。
- **I-3 三个固定承载**：**查看 = 右侧抽屉**（不遮表、可连续点下一行）；**编辑 = 弹窗**（带字段级校验 + `App.job` 步骤）；**跨页 = 跳转**（动作名以 `toXxx` 开头）。同一语义只允许一种，跨页同名按钮必须同一种承载。
- **I-4 每页必有下一步**：至少一个跳转或写入，禁止只读死端；只读页的出路是"去执行页"。
- **I-5 反馈只有一套**：`App.job` 三步动画 + `toast`；不新增第二套确认弹窗，不复用 `confirm` 表达非破坏性动作。

## 七、风险

- 查询过滤是**客户端过滤**（`applyFilters` 隐藏行），静态原型限定；真实系统应换成服务端查询并带分页，规则条文不变。
- 行内减动作不等于减能力：`models.detail` 抽屉里保留了全部原动作，只是换了位置；`_audit_actions` 的动作数从 323 涨到 325 可证。
- 计数改为整页聚合后，单表页的数字与以前一致，多表页从"最后一张表"变成"整页"，属修正而非回归。
